# 도구 라우팅 평가 — Epic 3

> 질문 텍스트를 도구 카테고리로 라우팅하는 두 기법(임베딩 top-k / LLM 분류)의 정량 비교입니다.
> 측정 스크립트: `backend/test/tool-routing.test.ts` · 골드셋: `backend/test/tool-routing-goldenset.json`
> 실행: `cd backend && npm run test:tool-routing` (Ollama + MCP 서버 구동 필요)

## 골드셋

- **20문항** = 단일 의도 16문항(카테고리 4개 × 4) + **복합 의도 4문항**
- 카테고리: `배송` · `주문·결제` · `고객·성분` · `법령·기능성`
- 복합 의도 예: "배송 중인데 이 제품 광고 문구도 괜찮은지 봐줘" → `배송` + `법령·기능성`
- 상태: **사용자 검수 확정 (2026-09-16)**

## 합격선 (Epic 3 설계 인터뷰에서 확정)

- 단일 의도 정확도: 임베딩 **≥ 0.80** / LLM **≥ 0.90**
- 복합 의도: 단일 의도 정확도가 아니라 **top-2 병합 시 recall**로 별도 측정
  (임베딩은 상위 2개 후보 집합, LLM은 실제 선택 집합 기준)

## 측정 결과 (2026-09-16)

| 라우터 | 단일 의도 정확도 | 복합 의도 top-2 병합 recall | 비고 |
|---|---|---|---|
| **임베딩 top-k** (`qwen3-embedding:0.6b`) | **81.3%** (13/16) | **87.5%** | LLM 호출 없음 · 임계값 0.36 |
| **LLM 분류** (`ollama/glm-5.3-flash:cloud`) | **100%** (16/16) | **100%** | 카테고리만 뱉는 짧은 호출 |

- 임베딩 오분류 3건: `order-1`("이 고객이 최근에 뭘 주문했어?" → 고객·성분) · `law-3`("오메가3의 기능성 원료 인정 내용" → 고객·성분) · `law-4`("품목제조신고 제품 정보" → 고객·성분)
- 임베딩은 **LLM 호출 0회**로 81%를 낸다는 점이 핵심이다 — 하네스가 언어 이해 없이도 의미 기반으로 후보를 좁힐 수 있다.
- LLM은 정확하지만 요청마다 호출 1회가 추가된다(지연·비용).

## 기법 선택

- **런타임 기본은 임베딩**이다(빠르고 무료, 합격선 충족).
- LLM 분류는 UI의 `라우팅 방식` 토글로 전환할 수 있고, 실패하면 임베딩으로 자동 폴백한다.
- 두 기법은 `ToolRouterService`의 같은 인터페이스(`route(question, { method })`)를 구현하므로 교체가 자유롭다.

## 튜닝 중 발견한 함정 (재현 주의)

카테고리 **설명 어휘**가 정확도를 지배한다. 처음에는 `고객·성분` 설명에 도메인 전역어 "건강기능식품"이 들어 있어 **법령 질의 4건이 전부 `고객·성분`으로 흡수**됐다(정확도 68.8%).

- 교훈: 카테고리 설명에는 **그 카테고리를 구분하는 말**만 넣는다. 여러 카테고리에 공통으로 등장하는 도메인 전역어는 라우팅을 망친다.
- 어휘를 정리해 68.8% → 81.3%로 올렸다(`CATEGORY_DESCRIPTIONS` 주석 참조).
- Qwen3-Embedding의 instruct 프리픽스(`Instruct: …\nQuery: …`)도 실험했으나 이 골드셋에서는 오히려 낮았다(75.0%).

## 안전장치

임베딩 top-1 점수가 임계값(0.36) 미달이면 **상위 2개 카테고리를 병합**해 도구를 함께 제공한다(recall 우선). 배송 질문이 지식 카테고리로 새는 것을 막기 위한 장치이며, 골드셋의 복합 의도 문항이 이 경로를 검증한다.
