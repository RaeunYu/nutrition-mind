# 0003 — 상거래 도메인 도입과 도구 호출 하네스

- 날짜: 2026-09-16
- 상태: 확정
- 맥락: 프로젝트는 법령·기능성 RAG 조회 도구로 시작해 사내 담당자용 도구로 확장됐다(ADR-0001). 그러나 상담 담당자의 실제 문의는 "이 고객의 물건이 안 왔다"처럼 주문·결제·배송 상태 조회에서 시작되며, 현재 데이터 모델에 그 개념이 전혀 없다. 또한 배경 문서 2장의 학습 목표인 Tool Calling 루프와 Tool Routing/Selection이 코드에 없다 — MCP 도구 4종은 외부 클라이언트 전용으로 노출돼 있을 뿐, 백엔드가 도구 스키마를 LLM에 주입하고 `tool_use`를 실행하는 루프가 없다.
- 결정:
  1. **상거래 도메인 5엔터티(주문·주문 항목·결제·배송·배송 이력)** 를 도입한다. 반품·교환·클레임은 비목표. 주문 항목은 I0030 품목제조신고 제품을 참조하고, 그중 25종을 단일 제품 풀로 선정해 섭취 제품과 주문 항목이 공유한다. 섭취 제품은 고객의 주문 항목에서 파생시킨다.
  2. **에이전트 하네스를 NestJS 백엔드에 둔다.** LangGraph는 도입하지 않고(별도 에픽에서 판단) 순수 코드로 루프를 구현하며, LLM 프로바이더 추상화(`llm.service.ts`)를 도구 지원형으로 확장한다.
  3. **도구 실행은 MCP 프로토콜 단일 경로로 한다.** 하네스가 `mcp` 서버의 `tools/list`로 카탈로그를 수신하고 `tools/call`로 실행한다. 상거래 도구는 Python MCP 서버에 추가해 HTTP·stdio 양쪽에 동시 노출한다.
  4. **도구 카탈로그는 4카테고리 13종** — 배송 3, 주문·결제 3, 고객·성분 3, 법령·기능성 4. 카테고리 메타데이터는 도구 description에 둔다.
  5. **도구 스키마 주입은 2모드** — 기본은 라우터가 카테고리를 정해 해당 도구를 사전 주입(A), 학습용으로 메타 도구 `list_tools`를 통한 동적 발견(B)을 토글 제공. 두 모드는 같은 카탈로그·실행기를 공유한다.
- 근거: 상담 담당자의 문의 동선이 주문·배송에서 시작하므로 이 도메인이 없으면 도구 라우팅 데모가 성립하지 않는다. 하네스를 NestJS에 두는 이유는 인증·고객 컨텍스트·접근 로그·LLM 추상화가 이미 그곳에 있어 새 서비스의 운영 비용만 늘기 때문이다. MCP 경유는 배경 문서 2.1의 3계층(LLM 서빙/하네스/MCP 도구)과 "`tools/list`로 스키마 자동 수신"이라는 학습 목표에 대응한다.
- 대안: (1) in-process 도구 실행 — 빠르지만 MCP 학습 목표가 사라짐. (2) 신규 Python 하네스 — LangGraph 재도입 비용을 미리 지불. (3) 도구 4종 유지 — 라우팅이 성립하지 않음. (4) 자체 제품 카탈로그 신설 — I0030 재사용 대비 이득 없음.
- 후속: 라우팅 기법(임베딩 vs LLM 분류)은 교체 가능한 인터페이스로 설계하므로 ADR로 고정하지 않고 골드셋 비교 결과를 문서로 남긴다.

## 비목표로 남긴 위험 (다음 에이전트 필독)

MCP 도구를 Python 서버에 추가하면 **Claude Desktop(stdio)에서도 상거래·고객 도구가 그대로 노출**된다(`run_stdio.py`가 `server.py`의 `mcp` 인스턴스를 그대로 import). 웹 경로는 JWT 로그인 뒤의 사내 담당자만 접근하지만, **MCP 외부 접근 경로에는 요청 단위 인증이 없다.** 실환경이라면 MCP 요청마다 별도 인증·권한 확인이 필요하다.

- 이는 현 구현 목표에서 **의도적으로 제외한 비목표**이며, 구현 누락이 아니다.
- 같은 사실을 `README.md`(사용자용)와 다음 에이전트용 HANDOFF 문서에도 기록한다.
- 접근 로그는 ADR-0002 개정에 따라 MCP 도구 실행 지점에서 기록해, 두 경로 모두 흔적은 남는다 — 그러나 이는 사후 기록이지 접근 통제가 아니다.
